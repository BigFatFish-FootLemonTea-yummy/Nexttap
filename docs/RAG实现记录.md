## 一、现状基线（改动前实测）

**评测集**：`data/rag/retrieval_eval.jsonl`，68 条 query → task_id

**纯词面召回（`guide.search` 原实现，未加同义词前的版本）**：

| 指标 | 数值 |
|---|---|
| Recall@1 | 17.6% |
| Recall@3 | 25.0% |
| Recall@5 | **26.5%** |
| MRR | 0.214 |
| 完全未命中 | **73.5%** |

### 为什么这么低

1. **`aliases` 是模板拼接的**，实测零贡献：
   ```
   "儿子的微信" / "怎么儿子的微信" / "我要儿子的微信" / "帮我儿子的微信"
   ```
   306 条 alias 里，306 条都是这种模板产物。

2. **词面天然稀疏**：中文短句里「退休金」和「养老保险」一个字都不重合。

3. **口语与按钮名不共享字符**：
   - 「交税那个」→ 目标「粤税通」
   - 「给孙子点零花钱」→ 目标「红包」
   - 「跟孙子说说话」→ 目标「视频通话」

4. **同屏多个相似入口**：「药费在哪儿交」vs「看完病在哪儿交钱」，
   目标分别是 `rx_pay` 和 `pay_bill`，字面上都含「交」「钱」。

## 二、技术路线决策

### 约束

| 约束 | 影响 |
|---|---|
| DeepSeek **不提供 embedding 接口**（`/v1/models` 只有 chat 模型） | 必须另找 embedding 来源 |
| 部署目标 **2C4G 纯 CPU**，OCR 已占 600–900MB | 本地跑 torch 会抢内存 |
| 技术文档 2.3 已写「Embedding 与 Rerank 上云」 | **与本次实现不一致，需改文档** |
| `guide.search()` 返回结构**不能变**（MCP `search_guide` 依赖） | 只能改内部实现 |

### 实际选了本地 ONNX

原计划走云端 embedding API（与 2.3 技术选型一致），但：

- DeepSeek 的 key **调不通**智谱/通义的 embedding 接口（服务商不同，401）
- 申请新平台的 key 需要额外时间，且评审意见 §三 明确建议
  「embedding + rerank 换 **onnxruntime** 后端，内存可砍一半」

**最终方案：`fastembed` + `BAAI/bge-small-zh-v1.5`（512 维，ONNX，约 90MB）**

> ⚠️ **这和技术文档 2.3 写的「上云」不一致，需要更新 2.3 那一节**，
> 否则评委对照代码和文档会发现矛盾。

### 索引规模

- 120 条任务链
- 索引文本 = `name + aliases（去模板）+ steps[].target`
- 一次性编码，进程内缓存；模型加载约 25 秒（含首次下载）

## 三、实现

### 三阶检索

```
query
  ├─ 词面召回（_score）：去填充词 + 同义词扩展 + 二字组重合度
  ├─ 向量召回（_VectorIndex）：bge-small-zh 余弦相似度
  ├─ RRF 融合（_rrf_fuse）：score = Σ 1/(60 + rank)
  └─ rerank（可选）：bge-reranker-base 交叉编码器重排 top-20
```

**为什么用 RRF 而不是分数加权**：词面是 0–1 相似度、向量是余弦距离，
量纲不同，直接加权要归一化且权重难调；RRF 只看排名，无需调参。

### 开关

环境变量 `NEXTTAP_RETRIEVAL`：

| 值 | 行为 |
|---|---|
| `lexical` | 只走词面 |
| `hybrid` | 词面 + 向量 + RRF（**默认**） |
| `hybrid_rerank` | 再叠 rerank（**线上别开，见下**） |

### 降级

`fastembed` 未安装或模型加载失败时，**自动退回纯词面，不抛异常**。
已实测：模拟 ImportError 后 `search()` 仍返回正确结果。

## 四、消融表（实测）

评测集 68 条，`python tools/eval_retrieval.py --ablation`

| 配置 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| 纯词面（基线，未加同义词） | 17.6% | 25.0% | 26.5% | 0.214 |
| 纯词面（**加了同义词表后**） | 30.9% | 45.6% | 47.1% | 0.373 |
| **+ 向量召回 + RRF** | **47.1%** | **73.5%** | **80.9%** | **0.612** |
| + rerank | 47.1% | 75.0% | 79.4% | 0.607 |

### 结论

1. **词面加同义词**：26.5% → 47.1%，**涨 20.6 个点**。
   印证了文档 §十二 的判断——「先修数据，再改算法」，收益最大的一步
   其实是补词典，不是上模型。

2. **向量 + RRF**：47.1% → 80.9%，**再涨 33.8 个点**。
   Recall@1 从 30.9% → 47.1%，MRR 0.373 → 0.612。
   这是真正的语义补位，词面完全盲区的样本（「交税那个」→「粤税通」）被救回来了。

3. **rerank 几乎没有增益**（Recall@5 反而从 80.9% 掉到 79.4%）。
   原因推测：RRF 的 top-20 里正确答案本来就少，rerank 重排空间有限，
   加上 bge-reranker-base 对中文短 query 效果一般。
   **且单次查询从 ~100ms 涨到 3.8s**，线上绝对不能开。

   > 评审意见 §三.3 早就说过：「线上不跑 rerank，只在离线做消融表」。
   > 实测印证了这个判断。

## 五、下一步（重要）

### 1. 评测集必须换真人版

当前 68 条是内部初版，**不能作为最终结论**。正确做法（文档 §十二 原方案）：

> 找 3 个人（至少一位长辈）把 top-30 任务各说一遍，用真实说法当评测集。

这件事和 **W2 的 5 人访谈是同一批人**，可以顺带做掉。

### 2. aliases 数据仍然没修

`paths.jsonl` 里 306 条模板 alias 还在。本次实现是在**代码里**绕过了它们
（`_index_text` 过滤 `怎么X/我要X/帮我X`），但**数据本身没动**。

修数据需要真人说法，同样依赖访谈。

### 3. 两处命名错仍未修

| task_id | 现在的 name | 应该是什么 |
|---|---|---|
| `hospital.pick_dept` | 神经医学科 | **选择科室**（它是 21 个科室的选择页） |
| `hospital.pick_slot` | 科室 | 待确认（步骤是「确认科室」） |

### 4. 差 9 个百分点的原因

19.1% 的 Miss 集中在两类：

- **同屏近义**：「药费在哪儿交」vs「看完病在哪儿交钱」→ `rx_pay` vs `pay_bill`
- **口语→具体入口**：「第一次来不知道去哪」→「就诊指南」

这类光靠 embedding 补不上，需要更细的 aliases。**还是回到数据。**
