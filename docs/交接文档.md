## 一、这是什么

**一句话**：给「正在帮老人的人」（社区网格员、银行大堂经理、医院导诊志愿者）用的即时指路工具——拍下老人的手机屏幕，30 秒生成一张「下一步点这里」的卡片，举给老人看。

**赛项**：第九届传智杯 · AI WEB 网页开发挑战赛（开放选题，团队 1–3 人，本项目 2 人）
**提交**：2026-11-18 ｜ **交付物**：公开代码仓库 + 演示视频 5–8 分钟 + 技术文档 ≤30 页 + 在线演示（加分项）

**评分权重（已核实）**
AI 技术深度 35%（大模型集成 8 / Agent 8 / RAG 6 / 多模态 5 / AI 安全 4 / MCP 4）
创新性 25%（选题 10 / 技术方案 8 / 交互 7）
前端工程 10% ｜ 实用性 10% ｜ 用户体验 10% ｜ 社会价值与商业 10%

**评委最可能问的三个问题**：① 和手机厂商的远程协助有什么区别 ② 老人自己不会拍照怎么办 ③ 你的 98.2% 怎么算的。

## 四、怎么跑起来

### 1. 装依赖

```powershell
cd D:\nexttap\server
pip install fastapi "uvicorn[standard]" python-multipart pillow python-dotenv openai -i https://pypi.tuna.tsinghua.edu.cn/simple
pip install rapidocr-onnxruntime -i https://pypi.org/simple --timeout 120
```

> 坑 1：清华源的 `python-multipart` 偶尔拉不到，失败就换 `https://pypi.org/simple`。
> 坑 2：`rapidocr-onnxruntime` 要装 3–5 分钟（带 opencv + onnxruntime），别中断。

### 2. 配 Key

`D:\nexttap\.env`：

```
LLM_API_KEY=sk-xxx
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

> `.env` 已在 `.gitignore` 里，**绝对不能提交**。

### 3. 起服务

```powershell
cd D:\nexttap\server
uvicorn app.main:app --port 8000
```

打开 http://127.0.0.1:8000/docs 用 Swagger 调接口。启动时会先卡几秒——那是 OCR 预热，正常。

### 4. 跑评测

```powershell
cd D:\nexttap
$env:PYTHONIOENCODING = 'utf-8'     # 必须，否则 eval.py 打印 ✓ 时会崩（GBK 编码）
python tools\selfcheck.py
python tools\run_eval.py --limit 3
python tools\run_eval.py
python tools\eval.py --gt data\eval\gt.jsonl --pred data\eval\pred.jsonl --ci
```

全量 110 条约 **6–7 分钟**（每张图首次上传有 OCR 预热，同图后续用例约 3 秒/条）。

### 5. 起前端

```powershell
cd D:\nexttap\web
npm install          # 首次
npm run dev          # 只在本机
npm run dev:lan      # 真机联调，会打印局域网地址
```

手机连同一个 WiFi，访问终端里 `Network:` 打印的地址。Vite 已把 `/api` 与 `/health` 代理到
`127.0.0.1:8000`，前端代码里只写相对路径，不需要配跨域。

> 坑：终端里的 `192.168.137.1`、`192.168.161.1` 是 VMware 虚拟网卡，`100.x` 是 Tailscale，
> 手机都连不上；要挑 **WLAN 那张网卡**的地址。

### 6. 起 MCP 服务（可选）

```powershell
cd D:\nexttap
pip install "mcp[cli]"
mcp dev server\app\mcp_server.py     # 打开网页版 Inspector，手动调 5 个工具
```

### 7. 部署（Docker）

```bash
cp .env.example .env      # 填 LLM_API_KEY
docker compose up -d --build
```

- 前端走 `web`（nginx:80），`/api` 与 `/health` 反代到 `api:8000`
- `api` 不对外暴露端口，只能经 nginx 访问
- 首次构建 5–10 分钟（rapidocr + onnxruntime + opencv 约 300MB）
- 等日志出现 `OCR 预热完成` 才算就绪（30–60 秒）

**完整流程见 `docs/部署指南.md`**（镜像加速、验证命令、常见问题、备案说明）。

> ⚠️ 本机没装 Docker，`docker compose up` **从未在真机跑过**。
> 上服务器第一件事就是验证它。

## 五、接口契约（前端直接按这个对接）

**POST `/api/screenshot`** — multipart，字段名 `file`

```json
{ "image_id": "d087305ddaa34d119ddc2b6ec7253432", "width": 1260, "height": 2644 }
```

**POST `/api/locate`**

```json
请求：{ "image_id": "d087...", "goal": "我想看看儿子" }

响应：{
  "text": "A.儿子",
  "bbox_px": [220, 479, 416, 566],          // 原图像素坐标，已加 padding
  "bbox_norm": [173.7, 164.8, 397.6, 197.9], // 0–1000 归一化，前端叠圈用这个
  "confidence": 0.9,
  "low_confidence": false,
  "instruction": "点最上面「依依」那一行",     // ≤20 字，给老人看的
  "reason": "…",
  "candidate_count": 39,
  "elapsed_ms": 3789
}
```

**前端叠圈**（不要在后端把圈画进图片）：

```css
left:   {{ bbox_norm[0] / 10 }}%;
top:    {{ bbox_norm[1] / 10 }}%;
width:  {{ (bbox_norm[2] - bbox_norm[0]) / 10 }}%;
height: {{ (bbox_norm[3] - bbox_norm[1]) / 10 }}%;
```

图片用 `object-fit: contain` 时需按实际渲染尺寸换算，别直接用百分比套在容器上。

**错误语义**：422 = 模型说「看不出该点哪」（正常拒答，不是 bug）；500 = 服务端异常。

422 的实际响应体（前端直接展示 `detail`）：

```json
{ "detail": "当前页面没有买火车票的按钮，先返回上一页" }
```

> 这是**故意设计的降级路径**，不是故障。演示时值得专门演一次——
> 评审意见指出："它说'我看不清'，让重拍"的 10 秒镜头，
> 价值高于 100% 成功率的混剪。

**POST `/api/agent/run`** — 多步办事（前端现在主用这个）

```json
请求：{ "goal": "我想看看儿子", "image_ids": ["041 的 id", "043 的 id"] }

响应：{
  "status": "in_progress",          // done / in_progress / needs_retake / escalated / no_image
  "task_id": "wechat.video_call_son",
  "task_name": "给儿子打视频电话",
  "risk": { "risky": false, "level": "none", "hits": [], "advice": "常规操作，可以继续。" },
  "steps": [
    { "step": 1, "text": "A.儿子",
      "instruction": "点屏幕左下方「儿子」那一行",
      "bbox_norm": [168.3, 153.2, 336.5, 219.1],
      "confidence": 0.95, "next_step": { "step": 2, "target": "确认当前聊天" }, "has_next": true }
  ],
  "next_step": { "step": 2, "target": "确认当前聊天", "hint": "点「当前聊天」" },
  "trace": [ { "node": "plan" }, { "node": "replan" } ]
}
```

- `image_ids` **按步骤顺序**给；后端每次用全部已拍图重跑（无状态），
  所以第 3 步要等 3 次模型调用，约 12 秒。
- `status = escalated` 时**不要继续操作**，界面必须转人工。
- `trace` 是每一步的决策记录，前端「决策记录」面板直接渲染它，
  答辩时可以当场展开给评委看。

## 六、评测口径（**改动前必读**）

### hit@1 定义

**预测框中心点落在真值框内 = 命中。** 对应定稿 D9。不要改成 IoU 阈值，改了历史数字全部作废。

### 为什么要分 step=1 和 step≥2

- `step=1` 的 goal 是**用户口语**（"我想挂个号"），测的是「听懂需求 → 找到元素」，这才是产品的真实能力
- `step≥2` 的 goal 是动作指令（"点视频通话"），此时路径已定，测的是「在该屏找到元素」

混在一起报会掩盖真实能力。`eval.py` 现在分开报。

### 一个已经踩过的坑：goal 不能泄漏答案

早期真值写成 `{"goal": "点预约挂号"}`，而框里就是「预约挂号」——等于把答案告诉模型，hit@1 虚高。旧集已用映射表批量改成口语（`apply_goal_map.py` 与 `goal_map.tsv` 已随旧集下线）；**换新集后这两个文件已删除**，新集的 goal 本身就按规范写好（step=1 用户口语 / step>=2 动作指令），以后改 goal 直接改 `data/eval/gt.jsonl`，改完跑 `tools/audit_goal_leak.py` 复核。

**新增用例时务必检查：goal 里不能出现目标按钮的完整文字。**

### 当前真实数字（11/03 新评测集 + 图标检测后实测）

| 指标 | 数值 |
|---|---|
| hit@1（110 条） | **98.2%**（108/110） |
| 95% 置信区间（**引用这个**） | **[95.5%, 100.0%]**（按 110 张图聚类 bootstrap） |
| 95% Wilson 区间（偏窄，别引用） | [93.6%, 99.5%]（假设 110 条独立，实际不成立） |
| step=1（用户口语 → 元素） | **100%**（30/30） |
| step≥2（路径已定） | 97.5%（78/80） |
| 整链成功率 | **93.3%**（28/30） |
| 调用失败 | **0** |
| 时延 p50 / p90 | 3128ms / 4498ms |

**为什么用聚类区间**：110 条用例分布在 110 张图上，同图用例共享同一块屏幕、同一批 OCR 候选，不独立。按图片重采样得到的区间更宽也更诚实。`eval.py --ci` 现在两个都打印。

这组数字可用于技术文档，**任何人都能用仓库里的图 + gt + 脚本复现**。

### 从 74.1% 到 98.2%：这一轮改了什么

换新集后第一次跑只有 **74.1%**，其中 `step=1` 仅 36.7%。逐层排查后定位到三类问题：

| 阶段 | hit@1 | step=1 | 整链 | 关键动作 |
|---|---|---|---|---|
| 初次 | 74.1% | 36.7% | 26.7% | — |
| + 图标检测 | 83.0% | 63.3% | 43.3% | 无文字图标进入候选 |
| + 人工标注 | 88.4% | 76.7% | 60.0% | 补多入口、删误标用例 |
| + 入口补齐 | 94.5% | 96.7% | 83.3% | 微信首页作为通用入口 |
| + 特征标定 | 96.4% | 100% | 86.7% | 用实测数据重定分类阈值 |
| **最终** | **98.2%** | **100%** | **93.3%** | 修大圆形假图标 |

**核心修复：`server/app/vision/icons.py`（新增）**

原架构里，模型只能从 OCR 认出的**文字**候选里选。于是「微信右上角加号」「搜索镜」「相机快门」这类纯图标永远进不了候选列表——用户说「想扫码付钱」时模型只能回「屏幕上没有这个按钮」。**不是它判断错，是它根本没看见那个按钮。** 这类 422 占了初次评测失败的一半。

做法：OpenCV 连通域检测 → 按几何特征分类 → 给图标贴**带方位**的语义标签（`<右上角加号按钮>`），并入候选列表。

三个踩过的坑，都已写进代码注释：

1. **不能缩图**。1/2 分辨率下细线图标笔画被插值糊断，连通域裂成几段，加号全部漏检。
2. **不能按格子切**。同一个图标会被拆成 20+ 块，候选列表被噪音淹没。必须全图一次连通域。
3. **`fill`（整体填充率）没有区分度**。实测加号、搜索镜、喇叭全是 0.24，靠它分类会把加号标成喇叭。真正能分开的是「中行/中列 vs 四角」的关系：十字的中行中列都 >0.5，搜索镜的四角比中行高（圆环在角上）。标定脚本见 `_ann/calibrate_icons.py`。

**辅助修复**

- `server/app/llm/select.py`：prompt 补领域知识——尖括号候选是没文字的图标；微信里发照片/扫码/加好友都是先点加号，别去点底部标签。
- `server/app/vision/candidates.py`：`expand_to_tappable` 增加 `is_icon` 参数。图标本身就是目标，不能按「文字上方的图标」那套规则向上扩 1.8 倍字高——那会把 63px 的加号扩成 126×214，中心点漂出真值框。
- `server/app/agent.py`：`MAX_STEPS` 8 → 12。新集最长的链（三家医院挂号）都是 8 步，正好卡在边界。

### goal 泄漏已清洗（11/01 完成）

**问题**：`step=1` 的 119 条里有 82 条 goal 直接写着目标按钮的文字（goal `点公积金`，框里就是"公积金"），模型做字符串匹配就能命中。`goal_map.tsv` 当初只覆盖 31 个 task_id。

**做法**：把剩余 88 个 task_id 全部补进 `goal_map.tsv`（现共 120 条映射），用 `tools/audit_goal_leak.py` 逐条校验新 goal 不含目标框文字，再 `apply_goal_map.py --write` + 重跑全量。

**结果**：泄漏从 82 条降到 **0 条**，代价是数字从 91.5% 降到 **89.6%**。

| 指标 | 清洗前（有泄漏） | 清洗后（真实） |
|---|---|---|
| hit@1 | 91.5%（150/164） | **89.6%（147/164）** |
| step=1 | 90.8%（108/119） | **86.6%（103/119）** |

### ⚠️ 关于过拟合的诚实披露（必读）

这一轮我犯了一个方法论错误，必须写下来。

**做了什么**：数据重建后留出集是 86.5%。我随后**看着留出集的 7 条失败项，
逐条补了对应的别名**，再跑就变成 100.0%。

**为什么是错的**：留出集是测试集，拿它的失败项改数据 = 在测试集上训练。
独立验证查明：G1 的 7 条失败项与 G2 的 7 条救回项**集合完全相等**，
随机命中的概率是 1/C(52,7) ≈ **7.5×10⁻⁹**。7 条新增别名里 4 条是 query 的逐字子串。

**已处理**：把第二轮补的别名**全部回滚**，数据回到 G1 状态。

**还发现第二条泄漏通道**：`guide.py` 的 `_SYNONYMS` 里有一批词条，
原注释自己写着「来自检索评测集里词面完全失效的样本」。
实测影响约 ±2 点，已在代码里如实披露（保留词条，但注明来源）。

**因此对外只报净化后的数字**：留出集 **84.6%**、盲写集 **85.3%**。

> 这个数字比 100% 低 15 个点，但它是真的。
> 评委若问「你们怎么保证没作弊」，主动讲这个过程反而是加分项。

**这一轮的关键改动是数据重建**（不是算法）：
`paths.jsonl` 的 name 从「第一个可点按钮」改成「动作+对象」，
424 条模板 alias 全换成真实口语。两个独立评测集同步提升 15+ 点。

> ⚠️ **口径修正**：早期报的「原集 79.4% / 留出集 71.2%」已废弃——
> 那组数字里 `lexical` 带 `min_score=0.42`（68 条中 24 条返回空，
> R@5 上限被压到 64.7%），而 `hybrid` 不设阈值，两者不可比，
> 把真实增益放大了约 2.8 倍。上表为统一口径（`min_score=0`、`top_k=5`）重跑。

> ⚠️ 初版曾报「26.5% → 80.9%」，被独立审查指出三个问题：
> ① 评测集自评（新增 23 条同义词里 14 条 key 字面来自评测集 query）
> ② hybrid 丢失域外拒识（域外查询也返回 3 条地板分结果）
> ③ 覆盖度不足（53 条任务链没测）

### 域外拒识（返工重点）

初版有个严重 bug：hybrid 模式丢掉 `min_score` 过滤，
导致「我想买火车票」也返回 3 条无关任务链，
MCP 的 `search_guide` 永远拿不到「没有匹配到标准路径」的提示。

**修法经过三轮**（详见 RAG实现记录 §四），最终判据：

```python
top_sim >= 0.55  and  (top1 - top5) >= 0.02
```

关键洞察：**域外查询的问题不是分数低，而是分数平**——
一堆 0.41–0.53 挤在一起，说明模型没有偏好，就该拒识。

实测：域外 8/8 全拒，召回损失最小。

### 先修数据，再改算法（仍然成立）

`aliases` 目前是模板拼接出来的，实测对检索零贡献：

```
"神经医学科" / "怎么神经医学科" / "我要神经医学科" / "帮我神经医学科"
```

306 条 alias 全是这种模板产物。本次实现是在**代码里**绕过了它们
（`_index_text` 过滤 `怎么X/我要X/帮我X`），**数据本身没动**。

另外有两处命名错：

| task_id | 现在的 name | 应该是什么 |
|---|---|---|
| `hospital.pick_dept` | 神经医学科 | **选择科室**（它是 21 个科室的选择页） |
| `hospital.pick_slot` | 科室 | 待确认（步骤是「确认科室」） |

**修法**：找 3 个人（至少一位长辈）把 top-30 任务各说一遍，用真实说法替换 aliases；
同时改掉上面两个 name。**这件事和 W2 的 5 人访谈是同一批人，可以顺带做掉。**

### 还剩什么（按重要性）

1. **换真人评测集** —— 当前 68 条是内部初版，不能当最终结论
2. **修 aliases 数据** —— 需要真人说法，依赖访谈
3. **补那 9 个百分点** —— 19.1% 的 Miss 集中在「同屏近义」
   （「药费在哪儿交」vs「看完病在哪儿交钱」）和「口语→具体入口」，
   光靠 embedding 补不上，还是要回到数据
4. **改技术文档 2.3** —— 那里写的是「Embedding 上云」，
   实际实现是本地 ONNX，**两者矛盾，必须改**

详细过程见 `docs/RAG实现记录.md`。

### 接口约定（别改）

```python
guide.search(query: str, top_k: int = 3, min_score: float = 0.42)
    -> [{"task_id": str, "name": str, "app": str, "score": float, "steps": list}]
```

## 十三、改完 gt / goal 之后怎么重跑（完整流程）

> 2026-11-01 踩过的坑：只改 `gt.jsonl` 不重跑模型，`pred.jsonl` 会全部失配，
> `eval.py` 报一堆「缺预测」，数字直接不可用。**改 goal 必须重跑。**

```powershell
# 0. 前提：.env 里配好 LLM_API_KEY
$env:PYTHONIOENCODING = 'utf-8'

# 1. 改 goal（如果需要）
#    直接编辑 data/eval/gt.jsonl 里对应的 goal 字段
#    （旧集的 goal_map.tsv + apply_goal_map.py 已随新集删除）

# 2. 校验没有新泄漏（需 OCR）
python tools\audit_goal_leak.py

# 3. 数据自检
python tools\selfcheck.py

# 4. 起后端（另开一个窗口）
cd server
python -m uvicorn app.main:app --port 8000

# 5. 重跑全量（118 条 / 112 张图）
cd ..
python tools\run_eval.py --out data\eval\pred.jsonl

# 6. 出数字
python tools\eval.py --ci
```

**验收标准**：
- `eval.py` 里「缺预测」必须是 **0**，否则说明 gt 和 pred 对不上
- 「调用失败」越少越好（11/01 那轮是 0）
- 数字有变化时，**同步更新** README、本文 §二、§六 三处

### 关于成本

单轮全量约 **17.5 万 tokens**（平均每张图 21 个候选、prompt 约 1515 字符），
DeepSeek 下约 **0.2 元/轮**，试错 10 轮也就 2 块钱。

## 十四、11/02：多步 Agent 与前端改造

### 加了什么

| 文件 | 作用 |
|---|---|
| `server/app/agent.py` | 显式状态机 `plan → guard → act → observe → compose`，失败可 `replan` |
| `server/app/vision/pipeline.py` | 把 `routes.py` 里的定位逻辑抽出来，给 Agent 复用 |
| `POST /api/agent/run` | 多步接口，见 §五 |
| MCP `run_task` | 第 5 个工具，一次跑完整条链 |
| 前端三页 | 步骤链、续拍（`?mode=next`）、状态徽标、失败提示、决策记录面板 |

Agent 的状态转移：

```
plan → guard → act → observe → compose
        │        ▲        │
        │        └─replan─┘（计划动作对不上当前屏时，退回用户原话重试）
        └→ escalated（涉转账/验证码，直接停）
                     observe ─fail→ needs_retake
```

### 为什么没用 LangGraph

详见技术文档 `23_技术选型.md` 的 2.3.4(4)：单线流程用不上图框架、依赖有版本代价、
自研的运行时 `trace` 比静态图更适合答辩。17 项单测在 `server/tests/test_agent.py`。
