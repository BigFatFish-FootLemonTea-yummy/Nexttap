## 2.1.2 分层职责

| 层 | 组件 | 职责 | 依赖 |
|---|---|---|---|
| **表现层** | Vue 3 三页 | 拍照、叠圈、全屏展示 | 仅 HTTP |
| **接入层** | Nginx | 静态托管 + 同域反代 | — |
| **服务层** | FastAPI | 路由、参数校验、错误语义 | — |
| **能力层** | vision / llm / guide | 三种 AI 能力 | 见下 |
| **数据层** | jsonl + 文件系统 | 任务链、截图 | — |

### 为什么 guide.py 是"纯逻辑"

`guide.py` 只依赖标准库（`json` / `re` / `difflib`），**不 import OCR、不 import 模型**。

这样做的收益：

1. **可以脱离环境单测**：`server/tests/test_guide.py` 14 项断言，不需要装 OCR
2. **可以独立演进**：检索算法从词面换成三阶，`test_guide.py` 一行没改
3. **可以被 MCP 直接复用**：MCP 进程不需要加载 OCR 模型

同理 `candidates.py`（候选合并 / padding / 归一化）也是纯逻辑，有独立单测。

**这条分层原则让"改算法"和"改集成"互不干扰。**

## 2.1.3 关键架构决策

### 决策 1：前端叠圈，后端不画图

**后端只返回归一化坐标**（`bbox_norm`，0–1000），由前端用 CSS 画圈。

| 方案 | 问题 |
|---|---|
| 后端画好圈再返回图片 | 每次定位要生成一张新图，多一次 IO；前端无法微调 |
| **前端叠圈（采用）** | 只传坐标；圈可拖动调整；图片用原图 |

代价是前端要处理 `object-fit: contain` 下的坐标换算：

```typescript
// 图片按 contain 渲染后，实际显示区域与容器不同
// 必须按真实渲染尺寸换算，不能直接套百分比
```

这是 `web/src/lib/box.ts` 的职责，有独立实现。

### 决策 2：单 worker

```dockerfile
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
```

2C4G 上，每个 worker 都要加载一份 OCR 模型（约 600MB）。两个 worker 就是 1.2GB，
加上系统开销必然 OOM。

**单 worker + 异步 IO 足够**：单次定位 2.7s 中 80% 是等 DeepSeek 返回，
是 IO 等待，不是 CPU 占用，async 可以让多个请求并发等待。

### 决策 3：同域反代，不分域

```
前端 → /api/locate（相对路径）→ Nginx → api:8000
```

**不分域的理由**：分域必然引入 CORS 与 Cookie 调试成本，而本项目没有任何
跨域需求。同域下前端代码里只写相对路径，`VITE_API_BASE` 留空即可。

### 决策 4：api 不暴露端口

```yaml
api:
  expose: ["8000"]      # 只对容器网络可见
web:
  ports: ["80:80"]      # 只暴露 80
```

避免 8000 直接暴露到公网被扫描/刷接口。

## 2.1.4 数据流：一次完整定位

```
① POST /api/screenshot  (multipart, file)
   ├─ 校验大小（≤8MB）与类型
   ├─ 存到 data/screenshots/YYYY-MM-DD/{uuid}.jpg
   └─ 返回 {image_id, width, height}

② POST /api/locate  {image_id, goal}
   ├─ 读图 → run_ocr()                    ~300–600ms
   │    └─ RapidOCR 输出逐行文字 + 框 + 分数
   ├─ merge_lines()                         ~1ms
   │    └─ 把同一卡片的多行文字合并成一个候选
   ├─ choose(candidates, goal, w, h)      ~1500–2500ms
   │    ├─ 构造 User Prompt（候选带编号 + 方位）
   │    ├─ 调 DeepSeek（temperature=0）
   │    └─ 解析 JSON → {id, confidence, instruction, reason}
   ├─ pad_box()                             ~1ms
   │    └─ 按行高向外扩展，让高亮像"可点区域"
   └─ to_norm()                             ~1ms
        └─ 像素坐标 → 0–1000 归一化

   ← {text, bbox_px, bbox_norm, confidence,
      low_confidence, instruction, reason,
      candidate_count, elapsed_ms}
```

**错误路径**：

| 情况 | 返回 |
|---|---|
| 图片不存在 | 404 |
| OCR 没识别到文字 | 422「没有识别到任何文字，请对准屏幕重拍」 |
| 模型返回 null | 422「屏幕上没有能…的按钮，先别点」 |
| 模型调用异常 | 500 |

## 2.1.6 为什么这样分层

一个反例说明分层的价值：

**问题**：检索算法要从纯词面换成三阶（词面 + 向量 + RRF + rerank）。

**如果 guide.py 和 OCR 耦合**（比如 import 了 `ocr.py`）：
- 每次改检索都要加载 OCR 模型才能测
- 单测跑不动（没有模型文件）
- MCP 进程也要背上 600MB 内存

**实际做法**：`guide.py` 只依赖标准库 + 可选的 `fastembed`：
- `test_guide.py` 14 项断言，纯 CPU，秒级
- fastembed 没装时自动降级为词面，不抛异常
- MCP 进程只加载检索，不加载 OCR

**这就是"纯逻辑模块"的实际收益。**

## 2.1.7 本章小结

架构的核心是三条：

1. **三层 AI 分工明确**：OCR 测量、模型判断、检索补路径，边界清晰；
2. **纯逻辑与集成分离**：`guide.py` / `candidates.py` 不依赖外部模型，可独立测试与演进；
3. **同域单机部署**：2C4G 单 worker，Nginx 反代，避免 CORS 与 OOM。

架构的复杂度刻意压在最低——22 天、2 个人的团队，
**能跑起来的简单架构优于跑不起来的先进架构**。
