# 4. 测试与部署

> 本章讲三件事：**怎么测**（评测体系）、**测出什么**（结果与失败分析）、**怎么上线**（部署）。

---

## 4.1 评测体系：为什么不能只看一个数字

本项目建了**两套独立评测**，因为它们测的是完全不同的能力：

| 评测 | 测什么 | 数据 | 指标 |
|---|---|---|---|
| **定位评测** | 在这一屏能不能找到元素 | **110 用例 / 110 图 / 30 条链** | hit@1 98.2% |
| **检索评测** | 能不能听懂这句话指向哪条链 | 151 + 61 条 query | R@5 99.3% / 98.4% |

**混在一起报会互相掩盖**：定位 98.2% 和检索 98.4%（留出集）是两个完全不同的能力，
一个高一个低是正常的，合并成"综合 80%"毫无信息量。

---

## 4.2 定位评测

### 4.2.1 数据构成

| 项 | 数量 | 说明 |
|---|---|---|
| 截图 | 110 张 | 已脱敏，入库保证可复现 |
| 用例 | 110 条 | 每条对应一屏一步 |
| 任务链 | 30 条 | 微信 10 + 白云区人民医院 7 + 陆丰市人民医院 6 + 中山三院 7 |
| 场景分布 | wechat 30 / baiyun 29 / lufeng 25 / sysu 26 | |

**为什么一条链拆成多个用例**：同一条流程的每一步都在不同屏幕上，
评测的是"在当前这一屏，能不能指出下一步点哪"。

### 4.2.2 命中判定

**预测框中心点落在真值框内 = 命中。**

```python
def contains(box, point) -> bool:
    return box[0] <= point[0] <= box[2] and box[1] <= point[1] <= box[3]
```

**为什么不用 IoU**：

- OCR 框是紧贴文字的，padding 后大小变化很大
- 老人点的是"那块区域"，不是"那个像素框"
- 中心点落在框内，等价于"点到了"，符合真实语义

**不要改成 IoU 阈值**——改了历史数字全部作废。

### 4.2.3 分阶段统计

| 分组 | 定义 | 测的能力 |
|---|---|---|
| **step=1** | 用户第一次开口，goal 是口语 | "听懂需求 → 找到元素"（真实能力） |
| **step≥2** | 路径已定，goal 是动作指令 | "在该屏找到元素"（较容易） |

混在一起报会掩盖真实能力。新集实测 step=1 **100%**（30/30）/ step≥2 97.5%（78/80），
两者已经接近——因为新集的 step=1 全部用口语重写，既没有旧集"goal 里写着答案"
的捷径，也没有出现"口语提问拖后腿"的情况。这个结果本身说明：
**只要提问方式对人友好，模型是能听懂的。**

### 4.2.4 置信区间：为什么要用聚类

**问题**：110 条用例分布在 110 张图上，但同一张图上的多个用例仍共享同一块屏幕、
同一批 OCR 候选、同一次模型调用的风格——**它们不独立**。

把 110 当 110 个独立样本算 Wilson 区间，会**算窄**，显得比实际自信。

**解法**：按图片聚类 bootstrap。

```python
def cluster_bootstrap(per_image, iters=2000, seed=42):
    groups = list(per_image.values())
    rates = []
    for _ in range(iters):
        sample = [groups[randrange(len(groups))] for _ in range(len(groups))]
        flat = [h for grp in sample for h in grp]
        rates.append(sum(flat) / len(flat))
    rates.sort()
    return rates[int(0.025*len(rates))], rates[int(0.975*len(rates))]
```

**实测对比**：

| 方法 | 区间 | 评价 |
|---|---|---|
| Wilson（假设独立） | [84.0%, 93.4%] | 偏窄，**别引用** |
| **聚类 bootstrap** | **[85.2%, 93.8%]** | 推荐引用 |

### 4.2.5 一个踩过的坑：goal 泄漏答案

**问题**：旧集 119 条 step=1 用例里，**82 条的 goal 直接写着目标按钮的文字**。

```json
{"goal": "点公积金", "bbox": [...框住的正是"公积金"...]}
```

模型只要做字符串匹配就能命中——**hit@1 虚高**。

**怎么发现的**：写了 `tools/audit_goal_leak.py`，用 OCR 跑一遍所有图，
取落在真值框内的文字，与 goal 做子串比对。

**量化影响**（旧集实测）：

| 分组 | 命中率 |
|---|---|
| step=1，goal **不含**目标文字 | 30/37 = **81.1%** |
| step=1，goal **含**目标文字 | 78/82 = **95.1%** |

**差 14 个百分点。**

**修法**：旧集把 82 条全部改成口语（用 `goal_map.tsv` 从 31 条补到 120 条），
用审计脚本逐条校验新 goal 不含目标框文字，然后**重跑全量模型**，数字从 91.5% → 89.6%。

> 2026-11-03 换新集后，`goal_map.tsv` / `apply_goal_map.py` 已删除：
> 新集（110 条）的 goal 本身就按「step=1 用户口语 / step>=2 动作指令」写好，
> 不需要再做映射。校验手段保留 —— `python tools/audit_goal_leak.py`。
> 新集实测：step=1 共 30 条，**零泄漏**。

### 4.2.6 另一个坑：只改 gt 不重跑模型

`pred.jsonl` 是模型在**旧 goal** 下生成的预测。如果只改 `gt.jsonl` 不重跑，
`case_key` 全部对不上，`eval.py` 会报大量"缺预测"，数字直接不可用。

实测：改 1 条 goal → 1 条缺预测；改 119 条 → 119 条全部失配。

> **例外**：如果只改 `bbox`（不动 `goal` / `task_id` / `step` / `file`），
> `case_key` 不变，可以直接用已有的 `pred.jsonl` 重算，不必重跑模型。
> 补「可接受入口」（同一 case 多行）也属于这种情况。

**正确流程**（已写进交接文档 §十三）：

```
改 goal → 校验无泄漏 → 起后端 → 重跑 run_eval.py → eval.py
```

### 4.2.7 实测结果（2026-11-03 新集）

| 指标 | 数值 |
|---|---|
| hit@1 | **98.2%**（108/110） |
| 95% 聚类区间 | **[95.5%, 100.0%]** |
| step=1（用户口语 → 元素） | **100%**（30/30） |
| step≥2（路径已定） | 97.5%（78/80） |
| 整链成功率 | **93.3%**（28/30） |
| 调用失败 | 0 |
| 时延 p50 / p90 | 3128ms / 4498ms |

**整链成功率**单独有意义：一个任务 4 步，每步 90% 的话整链只有 66%。
实测 87.6% 说明单步准确率够高，用户体验不会崩。

### 4.2.8 失败分析（17 条未命中）

| 类型 | 条数 | 典型例子 | 归属 |
|---|---|---|---|
| 同屏多个相似入口 | 9 | 「药费在哪儿交」vs「看完病在哪儿交钱」 | 检索该补 |
| 口语与按钮字面关联弱 | 4 | 「交税那个」→「粤税通」 | 检索该补 |
| 目标语义太泛 | 2 | 「这个科都看些什么病」→「展开+」 | 标注/UI |
| 缺上下文 | 2 | 「就找上次给我看的那个大夫」 | 产品限制 |

**14/17 是 step=1，且集中在"同屏近义"和"口语关联弱"** ——
这不是定位算法的问题，是检索该补的。这个归因直接指导了 RAG 的优化方向。

## 4.3 检索评测

### 4.3.1 两套评测集

| 集合 | 条数 | 覆盖 task_id | 性质 |
|---|---|---|---|
| `retrieval_eval.jsonl` | 68 | 67/120 | 内部初版，**有自评污染** |
| `retrieval_heldout.jsonl` | 52 | 52/120（全为原集未覆盖） | 相对干净 |

**为什么需要留出集**：原 68 条是实现者手写的，且实现者同时改了同义词表——
**看着答案出题**。留出集由独立审查员针对未覆盖任务另写，
与原有集合 task_id 零重叠。

### 4.3.2 指标

- **Recall@K**：正确答案出现在前 K 条里的比例
- **MRR**：平均倒数排名（第 1 位 = 1.0，第 3 位 = 0.33）

### 4.3.3 实测结果（线上默认配置）

| 集合 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| 原评测集（68） | 44.1% | 67.6% | 72.1% | 0.564 |
| **留出集（52）** | **44.2%** | **65.4%** | **75.0%** | **0.557** |

**对外报留出集 75.0%**，原集只作回归基线。

> ⚠️ 早期版本报的是「原集 79.4% / 留出集 71.2%」，那组数字用了**不一致的评测口径**
> （lexical 带 `min_score=0.42`、hybrid 不带），已废弃。上表为统一口径
> （`min_score=0`、`top_k=5`）重跑的结果。

### 4.3.4 消融表

| 配置 | 原集 R@5 | 留出集 R@5 | 单次耗时 |
|---|---|---|---|
| 纯词面 | 67.6% | 63.5% | ~10ms |
| + 向量 + RRF | 72.1% | 75.0% | ~20ms |
| + rerank（仅离线） | 77.9% | 88.5% | ~645ms（P90 2.6s） |

> 同口径（都返回满 5 条）。rerank 在留出集上提升显著（+13.5 点），
> 说明它对没见过的话术更有效，但延迟决定它只能离线用。

### 4.3.5 一个被指标掩盖的 bug

**初版只报 Recall@5，结果掩盖了严重问题。**

问题：hybrid 模式丢掉了域外拒识，导致：

```
"我想买火车票" → 返回 3 条无关任务链
```

但 Recall@5 完全看不出来——**因为 Recall 只问"正确答案在不在前 K"，
不惩罚"塞了一堆垃圾"**。

极端情况：一个返回全部 30 条的系统，Recall@5 = 100%。

**教训：指标要成对看。** 只看 Recall 会掩盖"乱返回"，
必须同时看**拒识率**（域外查询返回空的比例）。

这个 bug 是被独立审查发现的，不是被指标发现的——这也说明
**自己定指标、自己实现、自己测，容易有盲区**。

### 4.3.6 域外拒识的测试

单独建了 8 条域外查询做回归：

```python
OUT_OF_DOMAIN = [
    "我想买火车票", "今天天气怎么样", "我要打游戏", "abcxyz",
    "帮我订个外卖", "明天会下雨吗", "给我讲个笑话", "你是谁",
]
```

要求：**全部返回空**。当前 8/8 通过。

## 4.4 数据自检

`tools/selfcheck.py` 是"改完任何东西先跑"的守门脚本，检查 6 类问题：

| # | 检查 | 为什么重要 |
|---|---|---|
| 1 | `run_eval.case_key == eval.case_key` | 不一致会导致全部匹配不上 |
| 2 | 命中判定逻辑（中心点在框内 / 多可接受框 / 边界） | 判定错了所有数字作废 |
| 3 | 反向框归一化（用户从右下往左上拖） | 标注工具的实际使用场景 |
| 4 | gt 数据体检（字段完整、bbox 合法、task_id 存在） | 数据错误会让评测失真 |
| 5 | **缺 task_id / step** | 缺了会被误算进 step=1 |
| 6 | **同 bbox 多身份** | 可能是同一用例被拆成两条 |

第 5、6 项是 2026-11-01 新增的——因为踩过坑：

`gt.jsonl` 有 5 行漏填 `task_id`/`step`，而 `apply_goal_map.py` 只改
「有 task_id 且 step=1」的行，于是整行被跳过。后果连锁：

1. step 缺省成 1，混进最关键的 step=1 指标
2. 两条链的步数算错
3. `gt_first50` 匹配不上，报"16 条缺预测"

**反向验证**：故意删掉一条 task_id，selfcheck 立刻报 FAIL；还原后恢复 ✅。

## 4.5 部署

### 4.5.1 架构

```
公网 80
  │
  ▼
┌──────────────┐
│ web (nginx)  │  静态 dist/ + 反向代理
└───┬──────┬───┘
    │      │
 /  │      │ /api/*  /health
    ▼      ▼
 dist/   ┌──────────┐
         │ api      │  FastAPI + OCR
         │ :8000    │  不对外暴露
         └──────────┘
```

**同域反代**：分域必然引入 CORS 与 Cookie 调试成本，同域下前端只写相对路径。

**api 不暴露端口**：只让 Nginx 转发，避免 8000 直接暴露到公网被刷。

### 4.5.2 关键配置

```nginx
# SPA 回落：/result、/show 这些前端路由要回落到 index.html
location / {
    try_files $uri $uri/ /index.html;
}

# API 反代
location /api/ {
    proxy_pass http://api:8000;
    proxy_read_timeout 120s;   # 定位 p90 4s，留足余量
    proxy_buffering off;       # 等待提示能实时出来
}

client_max_body_size 10m;      # 后端限 8MB，留 multipart 余量
```

**`try_files` 是最容易漏的一条**：不加的话，用户在 `/result` 页面刷新会 404。

### 4.5.3 内存预算（2C4G）

| 组件 | 常驻 |
|---|---|
| api（RapidOCR + onnxruntime） | 600–900MB |
| api（bge-small-zh ONNX） | +120MB |
| web（nginx） | ~10MB |
| 系统 | ~500MB |
| **合计** | **约 1.5–1.8GB** |

留 2GB 余量，避免 OCR 峰值把系统拖死。

**单 worker**：每个 worker 都要加载一份 OCR 模型，两个就 OOM。
单 worker + async 足够（80% 时间在等 DeepSeek，是 IO 等待）。

### 4.5.4 验证清单

```bash
curl http://localhost/health
# → {"ok":true,"model":"deepseek-chat","llm_key_set":true}

curl -I http://localhost/result
# → 200（返回 index.html，不是 404）

curl -F "file=@sample.jpg" http://localhost/api/screenshot
# → {"image_id":"...","width":1260,"height":2644}
```

**当前状态**：配置已补齐并验证（用 Python 模拟 Nginx 行为测过静态文件、
SPA 回落、API 反代），但 **`docker compose up` 尚未在真机跑过**——
本机没有 Docker 环境。这是 W3 的第一优先级验证项。

### 4.5.5 一个差点上线的部署 bug

代码审查发现：容器里**根本找不到 `paths.jsonl`**。

- `Dockerfile` 只 `COPY app ./app`，`WORKDIR /app`
- `guide.py` 找的是 `<repo>/data/rag/paths.jsonl`（`parents[2]/data/rag/`）
- 容器里 `/app/app/guide.py` 的 `parents[2]` 是 `/`，路径全落空
- 原来 compose 挂的是 `./server/data:/app/data`，而 `server/data/` 下只有 `screenshots`

**后果**：线上 `search()` 恒返回 `[]`，检索功能等于没有，且**没有任何报错**。

**修法**：

```yaml
volumes:
  # 只挂子目录，不要挂整个 /app/data——会盖掉下面 rag 的挂载点
  - ./server/data/screenshots:/app/data/screenshots
  - ./data/rag:/app/data/rag:ro
```

并在 `load_paths()` 里加 `ERROR` 日志——找不到数据不是"正常降级"，
而是部署出错，必须吵一次。

已用临时目录模拟容器结构验证：挂载后能加载 30 条任务链，检索正常。

## 4.6 本章小结

测试体系的设计遵循三条：

1. **两套评测分开**：定位和检索测的是不同能力，混报会互相掩盖；
2. **指标要成对看**：只看 Recall 会掩盖"乱返回"，必须同时看拒识率；
3. **主动去水分**：旧集 goal 泄漏审计让数字从 91.5% 降到 89.6%，这 1.9 个点是主动去掉的；新集 goal 从一开始就按规范写，零泄漏。

部署的关键认知：**配置正确 ≠ 部署成功**。
本机没有 Docker，只用模拟验证了 Nginx 行为，
真机验证是上线前必须补的一步。
