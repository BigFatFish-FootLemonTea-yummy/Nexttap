# 2.3 技术选型

> 本章对应赛项对技术文档的要求之一：**"AI 技术的选型理由、集成方式、优化策略"**。本章只讲选型理由，集成方式见 2.4，优化策略见 2.5。
>
> 说明：文中标注【待实测】的数值为设计目标或估算值，须在 W3 用真实测量结果替换，不得直接作为结论提交。

---

## 2.3.1 选型约束

技术选型不是偏好问题，而是在既定约束下寻找**方差最小**的方案。本项目有五条硬约束：

| # | 约束 | 具体内容 | 对选型的影响 |
|---|---|---|---|
| C1 | 团队规模 | 2 人，无专职前端，依赖 AI 辅助编码 | 优先选择资料充分、AI 生成成功率高的成熟方案，不追新 |
| C2 | 开发周期 | 22 天（10/27–11/18） | 复用既有资产，任何"重学 + 重写"的方案直接排除 |
| C3 | 算力 | 单机 2C4G，纯 CPU，无 GPU | 不加载本地大语言模型；本地不常驻 torch |
| C4 | 交互时延 | 现场移动端使用，单次交互须 ≤5s | 端到端时延优先于模型能力上限 |
| C5 | 赛项形态 | Web 应用，明确考察 TypeScript、组件化、流式渲染 | 采用现代前端框架，不采用原生 App |

其中 C1 与 C2 是最强的两条：**在 22 天的项目里，团队熟悉度是优先级最高的技术指标**，其权重高于框架本身的先进性。

## 2.3.2 总体技术栈

| 层次 | 组件 | 版本策略 |
|---|---|---|
| 表现层 | Vue 3 + Vite + TypeScript + Tailwind CSS 3.4 + shadcn-vue | 锁定大版本，不追最新 |
| 状态与路由 | Pinia + Vue Router | — |
| 应用层 | FastAPI + uvicorn | — |
| 智能体层 | LangGraph（自定义 StateGraph） | 复用既有实现 |
| 检索层 | jieba BM25 + 云端 Embedding + 云端 Rerank + Chroma | — |
| 视觉理解 | RapidOCR（onnxruntime / CPU）+ Qwen-VL（仅图标兜底） | — |
| 语言模型 | DeepSeek（文本选择与文案生成） | — |
| 工具层 | fastmcp（4 个工具） | — |
| 存储层 | SQLite + 本地文件系统（7 天自动清理） | — |
| 部署层 | Docker Compose + Nginx 同域反向代理 | — |

整个栈可归纳为三层职责：**OCR 负责"测量"，语言模型负责"判断"，规则引擎负责"兜底"**。这一分工是后续所有选型的出发点。

## 2.3.3 逐项论证

### 2.3.3.1 前端层

| 项 | 约束 | 候选 | 取舍 | 结论 |
|---|---|---|---|---|
| 框架 | 团队有 Vue 3 经验；无专职前端；SSR 对本工具无收益 | Vue 3 / React + Next.js / Nuxt 3 | React 需 3–5 天/人学习并重写既有前端；Nuxt 多一层服务端渲染调试成本，换不来收益 | **Vue 3 + Vite** |
| 语言 | 赛项明确考察 "TypeScript 规范使用"（前端工程质量 4%） | TS / JS | TS 能让 AI 生成代码的接口错误在编译期暴露，减少运行期调试 | **TypeScript**（`strict: true`，关闭 `noUnusedLocals` 以适配 AI 生成代码） |
| 样式 | 用户体验 10%，需要"像产品"而非"像后台" | Tailwind 3.4 / Tailwind 4 / 原生 CSS | Tailwind 4 的配置模型变更，与 shadcn-vue 存在兼容风险；原生 CSS 开发速度不足以支撑 22 天 | **Tailwind 3.4**（禁止升级 4.x） |
| 组件 | 同上，且需 AI 生成稳定 | shadcn-vue / Element Plus / Naive UI | Element Plus 默认样式偏企业后台，产品感弱；shadcn-vue 视觉最接近"产品"，但有配置成本 | **shadcn-vue**，设 1 天 timebox，超时切换 Naive UI |
| 状态管理 | 页面间共享会话与卡片 | Pinia / Vuex / 自研 | Vuex 已非官方推荐；自研成本高 | **Pinia** |

### 2.3.3.2 AI 层

| 项 | 约束 | 候选 | 取舍 | 结论 |
|---|---|---|---|---|
| 元素定位 | 延迟 ≤5s，成本可控，失败可归因 | OCR + 文本模型 / VLM 直接输出坐标 | 详见 2.3.4(1) | **OCR + 文本模型**，VLM 仅兜底 |
| OCR | CPU 运行，中文界面，截图不外传 | RapidOCR / PaddleOCR / Tesseract / 云 OCR | PaddleOCR 需安装完整 Paddle 框架，体积与内存开销大；Tesseract 在中文 UI 场景识别率明显偏低；云 OCR 需外传截图，与隐私承诺冲突 | **RapidOCR**（onnxruntime） |
| 主模型 | 中文能力、JSON 可控、国内网络稳定 | DeepSeek / GPT-4o / 本地 7B | GPT-4o 成本与网络稳定性不占优；2C4G 无法承载 7B 模型，量化后质量亦不足以稳定完成候选选择 | **DeepSeek** |
| VLM | 仅处理无文字的图标 | Qwen-VL / 豆包 vision | 使用频次低，故选择按量计费的 API，不做本地部署 | **Qwen-VL / 豆包 vision** |
| Embedding | 2C4G，内存预算 ≤1GB | 本地 bge-small / 云端 API | 本地方案需常驻 torch，约 +600MB | **云端 API** |
| Rerank | 同上 | 本地 bge-reranker-base / 云端 API | 本地 reranker 约 1.5GB，直接超出内存预算 | **云端 API** |
| 向量库 | 单机部署，无独立服务 | Chroma / Milvus / Qdrant / pgvector | Milvus、Qdrant 需独立服务进程；pgvector 需额外引入 PostgreSQL | **Chroma**（嵌入式） |
| Agent 编排 | 需要向评审展示可解释的执行链路 | LangGraph / 自研状态机 / AutoGen / CrewAI | 自研等于重造轮子且无可视化产物；AutoGen、CrewAI 面向多智能体对话，对线性流程属过度设计，且调试困难 | **LangGraph StateGraph** |
| MCP 服务 | 需独立暴露工具能力 | fastmcp / 手写 JSON-RPC | 手写协议无收益 | **fastmcp** |

### 2.3.3.3 服务层

| 项 | 约束 | 候选 | 取舍 | 结论 |
|---|---|---|---|---|
| 应用框架 | 需与 Python 侧 OCR、检索生态对齐；需 SSE 流式 | FastAPI / Django / Flask | Django 的 ORM、Admin 在本项目中无使用场景；Flask 异步与流式支持较弱 | **FastAPI** |
| 数据库 | 单用户演示，无并发写入 | SQLite / PostgreSQL / MySQL | 引入独立数据库即多一个容器、多一类故障点 | **SQLite** |
| 消息队列 | 单用户，无异步任务编排需求 | 不引入 / RabbitMQ | 队列解决的是并发与削峰，本项目场景不存在该问题 | **不引入** |
| 缓存 | 无明显热点读 | 不引入 / Redis | 同上 | **不引入** |
| 部署 | 单机、需免 CORS、需可公网访问 | Docker Compose + Nginx 同域 / 前后端分域 / 平台托管 | 分域必然引入 CORS 与 Cookie 调试成本；平台托管对 Python + OCR 运行时支持受限 | **Docker Compose + Nginx 同域反代** |

## 2.3.4 三个关键取舍

### （1）元素定位：OCR + 文本模型，而非 VLM 直接输出坐标

这是本项目最核心的选型。大模型"看图给坐标"看似直接，但在本场景中存在四个问题：

| 指标 | VLM 直接输出坐标 | OCR + 文本模型 | 说明 |
|---|---|---|---|
| 单次延迟 | 5–8s【待实测】 | 2–3s【待实测】 | 现场交互对延迟极敏感 |
| 坐标精度 | 漂移较大，小字与图标尤甚 | 像素级准确（沿用 OCR 原框） | 定位错误直接导致老人点错 |
| 单次成本 | 高（图像 token） | 低（文本 token） | 千次调用成本相差一个量级 |
| 可解释性 | 黑盒 | 可打印完整候选列表 | 答辩与失败归因均需要 |
| 失败归因 | 难以区分"没看见"与"选错了" | 可区分 OCR 缺失与选择错误 | 决定迭代效率 |
| 图标支持 | 强 | 弱，需兜底 | 本方案的已知短板 |

**结论**：主链路采用 OCR 提取候选 → 语言模型在候选中选择 → 回填 OCR 坐标。VLM 仅用于无文字的图标场景，且只输出**区域**而非精确框。

一句话概括该分工：**让模型做它擅长的判断（选哪个），让 OCR 做它擅长的测量（在哪）。**

### （2）推理资源：Embedding 与 Rerank 上云，OCR 留在本地

C3 约束下的内存预算为 1GB，而本地推理方案的常驻开销如下：

| 方案 | 常驻内存 | 冷启动 |
|---|---|---|
| 本地 bge-small + torch | +600MB【待实测】 | 15–30s |
| 本地 bge-reranker-base + torch | +1.5GB【待实测】 | 20–40s |
| 云端 API | 0 | <100ms（不含网络） |

三者叠加将超出 2C4G 的可用内存，触发 OOM 或持续 swap，直接破坏 C4（交互时延）。

**隐私边界的澄清**：上云的是**操作路径文档的向量**，不包含任何用户截图。截图全程留在本地，仅在本地 OCR 与本地文件中处理。因此该取舍不与"截图不外传"的承诺冲突。

**结论**：OCR 本地化（涉及用户数据），Embedding 与 Rerank 上云（仅涉及公开文档）。离线消融实验可在本地临时加载模型完成，不影响线上部署。

### （3）前端：Vue 3 而非 React / Next.js

赛项推荐技术栈中同时列出了 React + Next.js 与 Vue 3 + Nuxt 3，且不做强制限定。选择依据是成本而非先进性：

| 方案 | 学习成本 | 复用既有前端 | SSR 对本工具的收益 | 结论 |
|---|---|---|---|---|
| Vue 3 + Vite | 0（团队已有） | 高 | 无 | **采用** |
| React + Next.js | 3–5 天/人 | 需重写 | 无（工具型应用，无 SEO 需求） | 否决 |
| Nuxt 3 | 1–2 天 | 中 | 无 | 否决 |

在 22 天的周期内，3–5 天/人的学习成本相当于总工时的 20% 以上，且不产生任何评分收益。

**结论**：Vue 3 + Vite。赛项对 SSR 无要求，首屏性能通过路由懒加载与资源压缩达成。

## 2.3.5 明确不采用的方案

| 方案 | 不采用的原因 |
|---|---|
| RabbitMQ | 单用户演示无并发与削峰需求，属纯负担 |
| Redis | 无热点读，缓存收益低于运维成本 |
| PostgreSQL / MySQL | SQLite 已满足单用户场景，独立数据库仅增加故障面 |
| Nuxt / Next.js | SSR 对工具型应用无收益，增加调试层 |
| Element Plus | 默认视觉偏企业后台，与"产品感"目标冲突（作为 shadcn-vue 的降级备选保留） |
| Tailwind CSS 4.x | 配置模型变更，与 shadcn-vue 存在兼容风险 |
| Tesseract | 中文 UI 场景识别率不足以支撑候选质量 |
| 云 OCR | 需外传用户截图，与隐私承诺冲突 |
| 本地 7B 语言模型 | 2C4G 无法承载，量化后质量不足以稳定选择候选 |
| 多智能体框架（AutoGen / CrewAI） | 本流程为线性状态机，多智能体属过度设计 |
| 原生 App | 赛项要求 Web 形态；且"扫码即用"是本产品的核心使用前提 |

## 2.3.7 备选与降级

| 风险 | 触发条件 | 降级方案 |
|---|---|---|
| shadcn-vue 配置受阻 | 1 天内未跑通 | 切换 Naive UI，放弃 Tailwind |
| 云端 rerank 不可用 | 接口异常或额度耗尽 | 退回 RRF 融合结果，关闭 rerank，转为纯混合检索 |
| DeepSeek 接口异常 | 超时或限流 | 重试一次 → 切换备用模型（同 prompt，JSON 约束不变） |
| OCR 识别率不足 | 反光/拍歪样本命中率低 | 增加图像预处理（透视矫正、对比度增强）；必要时引入云 OCR，并在文档中说明取舍 |
| 2C4G 内存不足 | 部署后 OOM | 升级 2C8G，或把 Chroma 改为远程实例 |

## 2.3.8 小结

本章的全部选型可归结为一句话：

> 在 2 人、22 天、2C4G、无专职前端的约束下，**优先选择方差最小的方案，而不是上限最高的方案**。

具体表现为四条原则：

1. **复用优先**：FastAPI、LangGraph、Vue 3 均来自既有项目，节省的 5–7 天直接转化为评测与访谈时间。
2. **分工明确**：OCR 测量、模型判断、规则兜底，三者边界清晰，失败可归因。
3. **资源匹配**：重模型上云，轻模型本地；内存预算内不加载 torch。
4. **保留降级**：每一项关键选型都配有触发条件明确的替代方案（见 2.3.7），避免单点失败导致项目停摆。
