# 1. 项目概述与需求分析

---

## 1.1 项目背景

### 1.1.1 一个被忽视的现场

中国有超过 1.5 亿老年人正在使用智能手机，但"会用"和"敢用"是两件事。

社区网格员、银行大堂经理、医院导诊志愿者每天要重复回答同一类问题：

> "闺女，这个码在哪儿点？"
> "我想看看我儿子，怎么弄？"
> "退休金那个在哪儿查？"

这些问题的共同特征是：**老人不是学不会，而是没有人告诉他下一步点哪里。**

### 1.1.2 现有方案的三个断层

| 方案 | 问题 |
|---|---|
| **子女远程指导** | 不在场。电话里说"你点那个圆的"，老人找不到 |
| **手机厂商远程协助** | 要装 App、要老人点同意、要共享整屏。老人更懵 |
| **去营业厅/找柜台** | 不在场，且无法覆盖居家场景 |

**三个断层**：远程的不在场、在场的不专业、专业的不即时。

### 1.1.3 一个反直觉的洞察

> "老人不是学不会用手机，是没有人告诉他下一步点哪里。"

顺着这句话往下推，会发现产品的本质**不是"一个卡片"，而是"一张能记住的图"**。

老人看完卡片要切回微信去点，卡片就没了。所以：

- 信息密度必须压到极限（≤25 字）
- 语音要**先播再让他切走**，而不是切走之后才播

这个"记住 vs 切走"的约束，直接决定了交互设计（见 1.4.2）。

## 1.2 产品定义

**一句话**：给"正在帮老人的人"用的即时指路工具——拍下老人的手机屏幕，
30 秒生成一张"下一步点这里"的卡片，举给老人看。

### 1.2.1 主用户不是老人

这是本项目最重要的一个决策，也是最容易被误解的地方。

| 角色 | 是谁 | 做什么 |
|---|---|---|
| **主用户：帮助者** | 社区网格员、银行大堂经理、医院导诊志愿者 | 拍下老人屏幕、输入目标、举手机给老人看 |
| **次用户：老人** | 60+ 岁，智能手机使用困难 | 低头点自己的手机，全程不碰任何新东西 |

**为什么这样定**：

如果主用户是老人，第一个问题就是"老人自己不会截图/拍照怎么办"——
这个问题无解。而把主用户换成帮助者，**这个矛盾直接消失**：
帮助者会用手机，拍照对他不是负担。

**产品形态因此是"双屏"**：

```
    帮助者的手机                    老人的手机
  ┌──────────────┐              ┌──────────────┐
  │  叠圈卡片     │              │              │
  │  ┌────────┐  │              │   微信界面    │
  │  │预约挂号│  │  举起来给     │              │
  │  └────────┘  │ ──────────▶  │  老人自己点    │
  │ "点下方靠右"  │    老人看     │              │
  └──────────────┘              └──────────────┘
```

两个人各一块屏，老人不需要学任何新东西。

### 1.2.2 明确不做什么

| 不做 | 理由 |
|---|---|
| **远程控制** | 红线：只教不做。接管老人手机有资金安全风险 |
| **全 App 覆盖** | 3 个场景起步（医院、政务、微信），做深不做广 |
| **微信登录** | 要资质，改用邀请码 + 角色 |
| **移动 App** | Web 优先，老人端 PWA |
| **子女远程场景** | 依赖分享链接 → 依赖备案 → 引入不确定性，本赛期封存 |

## 1.3 需求分析

### 1.3.1 场景一：医院（最刚需）

**现状**：三甲医院自助机 + 微信公众号双轨，老人两头都不会。

**典型任务链**：挂号

```
1. 我想挂个号              → 点「预约挂号」
2. 选神经医学科            → 点「神经医学科」
3. 选医生袁嘉蔚            → 点「袁嘉蔚」
4. 确认挂号详情            → 点「挂号详情」
```

**痛点**：
- 科室名老人不认识（"神经医学科"vs"我头晕该挂哪个科"）
- 同一屏有 21 个科室，字小、密
- 挂完号还要报到、缴费、查报告，每一步都是新界面

### 1.3.2 场景二：政务（最复杂）

**现状**：粤省事、穗好办、粤税通、粤医保……**多个小程序入口互相交叉**。

**典型任务链**：查社保

```
1. 我交了几年社保了   → 点「个人参保信息」
```

**痛点**：
- 入口名称是"黑话"（"穗好办"是啥？"粤税通"是啥？）
- 同一功能在 2–3 个 App 里都有入口，老人不知道点哪个
- 涉及人脸识别、实名认证，操作门槛高

### 1.3.3 场景三：微信（最高频）

**现状**：子女教过很多次，老人记不住。

**典型任务链**：给儿子打视频

```
1. 我想看看儿子        → 点「儿子的微信」
2. 确认当前聊天        → 点顶部「儿子」
3. 点视频通话          → 点右下角「+」里的「视频通话」
4. 选视频通话          → 点「视频通话」
```

**痛点**：
- 微信全是图标，没有文字提示
- "视频通话"这个词出现两次（菜单项 + 确认项），容易点错
- 老人最常问的就是这一类

### 1.3.4 需求优先级

| 优先级 | 需求 | 依据 |
|---|---|---|
| P0 | 拍屏 → 定位 → 大字卡片 | 核心链路，没有它产品不成立 |
| P0 | 失败时明确说"看不清" | 猜错让老人点错，比不点更糟 |
| P1 | 多步流程预判下一步 | 减少重复截图 |
| P1 | 高风险操作提醒 | 转账/验证码类操作要转人工 |
| P2 | 历史卡片复用 | "教完就忘"的痛点 |
| P2 | 语音播报 | 老人视力差，听比看容易 |

## 1.4 交互设计

### 1.4.1 三页流程

```
① 上传页              ② 结果页              ③ 全屏页
┌────────────┐      ┌────────────┐      ┌────────────┐
│ [拍照/选图] │      │ 叠圈 + 微调 │      │  白底大字   │
│ [我想挂个号]│ ──▶  │ 可拖动调整  │ ──▶  │  语音播报   │
│  [提交]    │      │ [给老人看]  │      │  屏幕常亮   │
└────────────┘      └────────────┘      └────────────┘
```

### 1.4.2 关键设计决策

| 设计 | 为什么 |
|---|---|
| **一键示例** | 答辩/演示现场不依赖拍照，避免翻车 |
| **常用口语 chips** | "我想看看儿子"这类高频说法一键填入，降低输入成本 |
| **人工微调** | AI 可能框偏，网格员可手动拖动，或一键退回原结果 |
| **全屏大字 56px** | `clamp(40px, 7vw, 56px)`，老人看得清 |
| **语音播报** | 老人视力差，且"先播再切走"对应"记住 vs 切走"约束 |
| **WakeLock 常亮** | 举着手机给老人看时屏幕不能灭 |
| **连点两下退出** | 单手可完成，且禁用双击缩放避免误触 |

### 1.4.3 一个被反复验证的细节

**instruction 必须 ≤20 字，且必须含方位 + 按钮上的字。**

反例：`"请点击屏幕下方偏右位置的预约挂号按钮"`
正例：`"点屏幕下方靠右的「预约挂号」"`

为什么这么严：

1. 老人记不住长句子
2. 只有按钮名不够——同一屏可能有多个同名按钮
3. 只有方位不够——老人不知道"下方靠右"具体是哪个

**方位 + 名称**，两者缺一不可。

## 1.6 本章小结

本项目的核心判断有三个：

1. **主用户是帮助者，不是老人**——这让"老人不会截图"这个死结直接消失；
2. **本质是"一张能记住的图"**——决定了信息密度和语音时机的设计；
3. **失败要诚实**——宁可说看不清，也不硬猜。

这三个判断贯穿了后续所有的技术选型与实现。
