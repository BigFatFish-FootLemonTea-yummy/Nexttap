# 2.4 AI 技术集成方式

> 本章对应赛项要求：**"AI 技术的集成方式"**。2.3 讲为什么选这些技术，本章讲这些技术**怎么接进产品**。

---

## 2.4.1 集成总览：三处 AI，一条主链路

本产品不是"调用一次大模型"，而是**三类 AI 能力各司其职、串成一条可解释的流水线**：

```
用户拍下屏幕截图
      │
      ▼
┌─────────────────────────────────────────────┐
│ ① OCR（本地，RapidOCR + ONNX）               │
│    作用：把像素变成「可选的文字块」            │
│    输出：候选元素列表（文字 + 像素框 + 置信度）│
└─────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────┐
│ ② 大语言模型（云端，DeepSeek）                │
│    作用：从候选里**选出**该点哪一个            │
│    输入：用户口语目标 + 候选列表（带方位）     │
│    输出：候选编号 + 置信度 + 一句给老人看的话  │
└─────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────┐
│ ③ 检索（本地，词面 + 向量 + RRF）             │
│    作用：从 120 条任务链里找到「标准操作路径」  │
│    用途：多步流程预判下一步，减少重复截图      │
└─────────────────────────────────────────────┘
      │
      ▼
   叠圈卡片（前端渲染，不在后端画图）
```

**核心设计原则：让模型做它擅长的判断，让 OCR 做它擅长的测量。**

这条原则来自一个具体的失败教训：如果让视觉大模型（VLM）直接从截图输出坐标，
实测坐标漂移严重（常在几十到上百像素），而且单次调用 5–8 秒。
而 OCR 给出的框是**像素级精确**的——它本来就在做文字检测。

因此本项目的分工是：

| 环节 | 谁做 | 为什么 |
|---|---|---|
| **在哪**（坐标） | OCR | 文字检测本来就是像素级的，不漂移 |
| **选哪个**（决策） | 大语言模型 | 理解"我想看看儿子"要对应"视频通话"，是语义判断 |
| **兜底** | 规则 | 置信度低时明确说"看不清"，不硬猜 |

## 2.4.2 环节一：OCR 的集成

### 为什么不用云 OCR

| 维度 | 本地 RapidOCR | 云 OCR（腾讯/百度） |
|---|---|---|
| 隐私 | 截图**不出机器** | 截图需上传 |
| 成本 | 0 | 有免费额度，超量收费 |
| 时延 | 约 300–600ms | 网络往返 + 排队，约 500–1500ms |
| 准确率 | 中文印刷体够用 | 略高 |

**决策：本地。** 理由是产品的安全叙事——"只传一帧静态画面，不建立实时屏幕共享"。
如果截图要上云做 OCR，这个承诺就站不住了。

### 集成的两个关键处理

**（1）候选合并**（`server/app/vision/candidates.py`）

OCR 输出的是**逐行文字框**，但用户点的是**可点区域**。两者粒度不同：

```
OCR 原始输出：             合并后：
┌─────────┐                ┌──────────────────┐
│ 预约挂号 │                │  预约挂号         │
└─────────┘                └──────────────────┘
┌─────────┐
│  门诊   │  ← 同一张卡片的      ↑ 合并成一个候选
└─────────┘     两行文字
```

合并规则：纵向距离 < 行高 0.6 倍、横向有重叠的文字框视为同一元素。
这是纯逻辑，有单元测试（`server/tests/test_candidates.py`）。

**（2）padding 扩展**（`pad_box`）

OCR 框是**紧贴文字**的，但真实可点区域更大。如果只高亮文字，
老人会去点字，而实际要点头像或整张卡片。

因此输出前按行高向外扩展一定比例，让高亮框看起来像"一个能点的块"。

> ⚠️ 评审意见指出这还不够：应该**对齐到最近的卡片/行边界**。
> 当前实现只是等比 padding，属于已知改进项。

### 预热

OCR 模型加载需要 5–10 秒。如果放在第一次请求里，用户第一次使用会以为卡死。

因此在 FastAPI 的 `lifespan` 启动钩子里**预热**：

```python
@asynccontextmanager
async def lifespan(_app: FastAPI):
    try:
        _engine_instance()   # 触发模型加载
    except Exception:
        pass                 # 预热失败不阻塞启动，只是首次变慢
    yield
```

## 2.4.3 环节二：大语言模型的集成

### Prompt 设计（`server/app/llm/select.py`）

**System Prompt 的六条规则，每条都对应一个踩过的坑：**

| 规则 | 对应的实际问题 |
|---|---|
| 只选一个；文字相同时用位置区分 | 微信里三个"视频通话"图标 |
| 没有候选能推进目标时返回 null，**不要硬猜** | 硬猜会让老人点错，比不点更糟 |
| instruction ≤20 字，必须含方位 + 按钮上的字 | 老人记不住长句子 |
| 只念核心文字，不念数字/日期/未读数 | 说"依依 5.24"不如说"依依那一行" |
| confidence 是 0–1 的把握 | 用于低置信度降级 |
| 只输出 JSON | 避免解析失败 |

**User Prompt 的结构**：

```
用户目标：我想看看儿子
屏幕尺寸：1260x2644
候选元素（共 21 个）：
[0] 屏幕上方靠左  "微信"      (120, 80, 380, 160)
[1] 屏幕中部      "依依 5.24" (8, 434, 1252, 610)
...
输出格式：{"id": 3, "confidence": 0.86, "instruction": "...", "reason": "..."}
```

**关键设计：给候选编号 + 方位描述，不给坐标让模型算。**

模型不擅长算坐标，但擅长"屏幕上方靠左的第二个"。所以候选列表里
同时给出**归一化位置描述**和**像素框**，让模型用位置区分同名元素，
但不需要它输出坐标——它只需要输出一个整数编号。

### 调用参数

```python
temperature=0   # 同一个输入要可复现，评测才有意义
```

### 输出解析的健壮性

模型可能返回 `{"id": 3}` 也可能返回带 markdown 代码块的 ` ```json {...} ``` `。
`select.py` 里用正则提取第一个 JSON 对象，解析失败则抛出，
由上层转成 422（"看不出该点哪"），而不是 500。

### 错误语义

| 状态码 | 含义 | 前端表现 |
|---|---|---|
| 200 | 成功定位 | 叠圈 + 卡片 |
| **422** | 模型明确说"看不出该点哪" | **正常拒答**，提示换张图/重说 |
| 500 | 服务端异常 | 提示稍后重试 |

**422 不是 bug，是设计的降级路径。** 这一点在演示时值得专门展示：
宁可说"看不清"，也不硬猜。

## 2.4.4 环节三：检索的集成

### 三阶检索

```
query "退休金那个"
   │
   ├─ ① 词面召回：去口语填充词 + 同义词扩展 + 二字组重合度
   │     → 候选排名（可解释，但中文短句字面稀疏）
   │
   ├─ ② 向量召回：bge-small-zh-v1.5 编码，余弦相似度
   │     → 候选排名（补语义，但可能语义沾边字面无关）
   │
   ├─ ③ 域外拒识：绝对阈值 + 相对领先
   │     → 没听懂就返回空，不硬凑
   │
   └─ ④ RRF 融合：score = Σ 1/(60 + rank)
         → 最终 top-k
```

### 为什么用 RRF 而不是分数加权

词面分数是 0–1 的相似度，向量分数是余弦距离（-1 到 1），**量纲不同**。
直接加权需要先归一化，而归一化方式本身又会引入偏差，权重也难调。

RRF（Reciprocal Rank Fusion）**只用排名不用分数**：

```
score(d) = Σ weight_i / (k + rank_i(d))     k = 60
```

无需调参，实践中更稳。k=60 是原论文的常用值，作用是压平头部差异。

### 域外拒识：一个反直觉的发现

集成时踩的坑值得单独说，因为它推翻了"阈值越高越安全"的直觉。

**问题**：初版 hybrid 模式丢掉了 `min_score` 过滤，导致"我想买火车票"
这类域外查询也返回 3 条无关任务链。

**第一直觉**：加一个向量相似度阈值（≥0.45）。

**实测失败**：

```
"我要打游戏"      → map.taxi  相似度 0.524   （域外，但分很高）
"给孙子点零花钱"  → 红包     相似度 0.535   （域内，只高 0.011）
```

bge-small-zh 对中文短句的区分度不足以靠绝对值分开。

**第二直觉**：要求"字面必须有交集"。

**实测更糟**：砍掉 14 条正确答案，包括"给他转点钱"→转账（0.770）。

**最终方案**：绝对阈值 + **相对领先**。

```python
top_sim >= 0.55  and  (top1 - top5) >= 0.02
```

**关键洞察：域外查询的问题不是分数低，而是分数平。**
一堆 0.41–0.53 挤在一起，说明模型对这句话没有任何偏好——那就该拒识。
域内查询通常 top1 明显领先。

实测：域外 8/8 全拒，召回损失最小。详见 `docs/RAG实现记录.md`。

## 2.4.5 MCP 的集成

### 为什么做 MCP

MCP（Model Context Protocol）让**任意 MCP 客户端**（Claude Desktop、Cursor 等）
可以直接调用本产品的能力，而不需要用户复制粘贴截图。

这对应评分项里的"Agent 与工具调用"——产品不只是一个网页，
它的能力可以被别的 Agent 编排。

### 四个工具

| 工具 | 作用 |
|---|---|
| `locate_element(image_path, goal)` | 定位元素 |
| `search_guide(query, top_k)` | 检索任务路径 |
| `check_risk(text)` | 判断是否高风险操作 |
| `compose_card(text, instruction, task_id, step)` | 组装卡片，带"下一步是什么" |

### 集成的两个工程细节

**（1）stdio 模式下 stdout 被协议占用**

```python
def _log(message: str) -> None:
    """stdio 模式下只能往 stderr 打日志。"""
    print(f"[nexttap-mcp] {message}", file=sys.stderr)
```

任何 `print()` 到 stdout 都会让客户端解析协议失败。

**（2）返回结构必须稳定**

`search_guide` 内部调用 `guide.search()`。这个函数的返回结构
`[{task_id, name, app, score, steps}]` 是**契约**，
内部实现从纯词面换成三阶检索，结构一行没变。

## 2.4.6 端到端数据流（一次完整调用）

```
① POST /api/screenshot  (multipart, 字段 file)
   ← {image_id, width, height}
   后端：存图 + 记尺寸，不在这里做 OCR

② POST /api/locate  {image_id, goal}
   后端内部：
      a. 读图 → run_ocr()          ≈ 300–600ms
      b. merge_lines() + pad_box()  ≈ 1ms
      c. choose() 调 DeepSeek       ≈ 1500–2500ms
      d. to_norm() 转归一化坐标      ≈ 1ms
   ← {text, bbox_px, bbox_norm, confidence,
      low_confidence, instruction, reason,
      candidate_count, elapsed_ms}
```

**实测时延**（110 条用例）：p50 = 2887ms，p90 = 4144ms，均满足 C4（≤5s）。

其中大模型调用占 80% 以上，OCR 约 15%。这也是为什么优化重点是
**减少模型调用次数**（多步预热），而不是优化 OCR。

## 2.4.7 集成的可解释性设计

产品的用户是"正在帮老人的人"，他需要知道**为什么**系统指向那里。

因此每次定位都返回：

| 字段 | 给谁看 |
|---|---|
| `instruction` | 老人（大字 + 语音） |
| `reason` | 帮助者（为什么选这个） |
| `candidate_count` | 帮助者（屏幕上有多少个可选元素，判断是否拍全） |
| `confidence` / `low_confidence` | 帮助者（要不要重拍） |

**这是"可解释"落到产品上的具体形式**：不是给一段模型思考过程，
而是给出帮助者当下需要的那几个判断依据。

## 2.4.8 小结

本章说明三处 AI 的集成方式，核心是三条：

1. **分工明确**：OCR 测量、模型判断、规则兜底，边界清晰，失败可归因；
2. **契约稳定**：`search()` 的返回结构、`/api/locate` 的响应字段
   是前后端与 MCP 的共同契约，内部实现可换；
3. **降级优先于硬猜**：422 是设计的一部分，不是异常。

集成方式的取舍全部指向一个目标：**在现场 30 秒内给出一个老人能看懂的答案，
且失败时诚实地说看不清。**
