## 3.1 核心功能一：元素定位

### 3.1.1 问题拆解

用户输入："我想挂个号" + 一张截图。
期望输出：屏幕上「预约挂号」那个按钮的坐标。

这实际上是**两个子问题**：

| 子问题 | 本质 | 谁擅长 |
|---|---|---|
| **在哪**（坐标） | 文字检测 | OCR（像素级精确） |
| **选哪个**（决策） | 语义匹配 | 大语言模型 |

如果让一个视觉模型同时做这两件事，就是让它在输出坐标的同时做语义判断——
实测坐标漂移严重（几十到上百像素），且单次 5–8 秒。

**拆开的收益**：坐标由 OCR 保证精确，模型只需输出一个整数编号。

### 3.1.2 步骤一：OCR 与候选构建

```python
# server/app/vision/ocr.py
def run_ocr(image_path: str, min_score: float = 0.5) -> List[Candidate]:
    result, _ = _engine_instance()(image_path)
    cands = []
    for item in result:
        pts, text, score = item[0], item[1], float(item[2])
        if not text or score < min_score:
            continue
        xs = [p[0] for p in pts]
        ys = [p[1] for p in pts]
        cands.append(Candidate(
            idx=len(cands),
            text=text.strip(),
            box=Box(min(xs), min(ys), max(xs), max(ys)),
            score=score,
        ))
    return cands
```

**延迟导入**是关键设计：

```python
def _engine_instance():
    global _engine
    if _engine is None:
        from rapidocr_onnxruntime import RapidOCR   # 延迟到这里才 import
        _engine = RapidOCR()
    return _engine
```

这样没有装 OCR 依赖时，其它模块（如 `guide.py`）仍然可以正常 import 和测试。

### 3.1.3 步骤二：候选合并（纯逻辑，有单测）

**问题**：OCR 输出的是**逐行文字框**，但用户点的是**可点区域**。

```
OCR 原始（3 个框）：        合并后（1 个候选）：
┌──────────┐
│ 预约挂号  │  ← 标题
└──────────┘
┌──────────┐                ┌────────────────┐
│ 剩余 12   │  ← 副标题      │   预约挂号      │
└──────────┘                └────────────────┘
┌──────────┐
│  可预约   │  ← 状态
└──────────┘
```

**合并规则**（`candidates.py`）：

```python
def merge_lines(cands: List[Candidate]) -> List[Candidate]:
    """纵向距离 < 行高 0.6 倍、横向有重叠的文字框视为同一元素。"""
```

参数 0.6 是试出来的：太小会把相邻卡片合并，太大则同一卡片拆成两个。

**为什么这段是纯逻辑**：它不依赖 OCR、不依赖模型，输入是 `List[Candidate]`，
输出也是。所以可以精确单测（`test_candidates.py`）。

### 3.1.4 步骤三：padding 扩展

OCR 框紧贴文字。如果只高亮文字，老人会去点字，而实际要点头像或整张卡片。

```python
def pad_box(box: Box, img_w: int, img_h: int) -> Box:
    """按行高向外扩展，让高亮看起来像"一个能点的块"。"""
    h = box.y1 - box.y0
    pad_y = h * 0.35
    pad_x = h * 0.6
    return Box(
        max(0, box.x0 - pad_x),
        max(0, box.y0 - pad_y),
        min(img_w, box.x1 + pad_x),
        min(img_h, box.y1 + pad_y),
    )
```

> ⚠️ **已知不足**：评审意见指出应"对齐到最近的卡片/行边界"，
> 当前只是等比 padding。这是 W3 的改进项。

### 3.1.5 步骤四：模型选择目标

**Prompt 设计**（`llm/select.py`）：

```python
SYSTEM_PROMPT = (
    "你是手机界面操作助手，服务对象是不会用智能手机的老人。"
    "根据用户的自然语言目标，从候选元素中选出【下一步应该点击的那一个】。\n"
    "规则：\n"
    "1. 只选一个；有多个文字相同的候选时，必须用位置或上下文区分。\n"
    "2. 如果没有任何候选能推进目标，id 返回 null，不要硬猜。\n"
    "3. instruction 必须是一句老人能听懂的话，不超过 20 个字，"
    "必须包含方位和按钮上的字。\n"
    "4. instruction 里只念按钮上的核心文字，不要念数字、日期、时间、未读数。\n"
    "5. confidence 是你对这次选择的把握，0 到 1 之间的小数。\n"
    "6. 只输出 JSON，不要解释。"
)
```

**每条规则都对应一个实际踩过的坑**：

| 规则 | 踩过的坑 |
|---|---|
| 1. 同名时用位置区分 | 微信里有三个"视频通话" |
| 2. 不能推进时返回 null | 模型硬猜，老人点错 |
| 3. ≤20 字 + 方位 + 名称 | 长句子老人记不住；只有名称分不清同名 |
| 4. 不念数字 | 说"依依 5.24"不如说"依依那一行" |
| 5. confidence | 用于低置信度降级 |
| 6. 只输出 JSON | 避免解析失败 |

**User Prompt 的候选格式**：

```python
def build_user_prompt(cands, goal, img_w, img_h) -> str:
    lines = "\n".join(c.prompt_line(img_w, img_h) for c in cands)
    return (
        f"用户目标：{goal}\n"
        f"屏幕尺寸：{img_w}x{img_h}\n"
        f"候选元素（共 {len(cands)} 个）：\n{lines}\n\n"
        '输出格式：{"id": 3, "confidence": 0.86, '
        '"instruction": "点屏幕最下方中间的\\"视频通话\\"", "reason": "简短理由"}'
    )
```

每个候选长这样：

```
[3] 屏幕上方靠左  "预约挂号"   (847, 1566, 1098, 1874)
```

**关键：给编号 + 方位描述，不给坐标让模型算。**
模型不擅长算坐标，但擅长"屏幕上方靠左的第三个"。

### 3.1.6 步骤五：输出解析

模型可能返回裸 JSON，也可能包在 markdown 代码块里：

```python
def _extract_json(text: str) -> dict:
    """从模型输出里提取第一个 JSON 对象。"""
    m = re.search(r"\{.*\}", text, re.S)
    if not m:
        raise ValueError(f"模型没有返回 JSON：{text[:200]}")
    return json.loads(m.group(0))
```

解析失败 → 抛异常 → 上层转 422（不是 500），因为"模型没按格式返回"
在产品语义上属于"没听懂"，不是服务故障。

### 3.1.7 实测结果

| 指标 | 数值 |
|---|---|
| hit@1 | **89.6%**（147/164） |
| step=1（用户口语） | 86.6%（103/119） |
| step≥2（路径已定） | 97.8%（44/45） |
| 时延 p50 / p90 | 2663ms / 4031ms |

**失败模式分析**（17 条未命中）：

| 类型 | 条数 | 例子 |
|---|---|---|
| 同屏多个相似入口 | 9 | 「药费在哪儿交」vs「看完病在哪儿交钱」 |
| 口语与按钮字面关联弱 | 4 | 「交税那个」→「粤税通」 |
| 目标语义太泛 | 2 | 「这个科都看些什么病」→「展开+」 |
| 缺上下文 | 2 | 「就找上次给我看的那个大夫」 |

**规律**：14/17 是 step=1，且集中在"同屏近义"和"口语关联弱"两类。
这正是检索（而非定位算法）该补的——见 3.2。

## 3.2 核心功能二：路径检索

### 3.2.1 为什么需要检索

定位解决的是"这一屏点哪里"。但一个完整任务有 1–4 步：

```
1. 我想看看儿子      → 点「儿子的微信」
2. 确认当前聊天      → 点顶部「儿子」
3. 点视频通话        → 点「+」→「视频通话」
4. 选视频通话        → 点「视频通话」
```

如果每步都要重新截图 + 调模型，一个任务 4 次调用 ≈ 11 秒，且老人要反复拍照。

**检索的作用**：命中任务链后，直接知道后面几步是什么，可以预判。

### 3.2.2 数据：120 条任务链

`data/rag/paths.jsonl`：

```json
{"task_id": "wechat.video_call_son",
 "name": "儿子的微信",
 "app": "wechat",
 "aliases": ["儿子的微信", "怎么儿子的微信", ...],
 "steps": [
   {"step": 1, "screen": "", "target": "点儿子的微信", "hint": "点「儿子的微信」"},
   {"step": 2, "screen": "", "target": "确认当前聊天", "hint": "点「当前聊天」"},
   ...
 ]}
```

> ⚠️ `aliases` 是模板拼接的，实测零贡献。这是已知问题（见 2.5.2）。

### 3.2.3 三阶检索的实现

**第一阶：词面召回**

```python
def _score(query: str, path: dict) -> float:
    query_variants = _expand(_clean(query))   # 去填充词 + 同义词扩展
    best = 0.0
    for alias in path.get("aliases") or []:
        alias_clean = _clean(alias)
        for q in query_variants:
            best = max(best, _sim(q, alias_clean))
            if len(q) >= 2 and q in alias_clean:
                best = max(best, 0.9)          # 子串命中给高分
    # name 略降权
    # steps[].target 只给 0.6（通用词会到处命中）
    return best
```

**第二阶：向量召回**

```python
class _VectorIndex:
    def _load(self):
        from fastembed import TextEmbedding
        self._model = TextEmbedding(model_name="BAAI/bge-small-zh-v1.5")
        texts = [_index_text(p) for p in self.paths]
        vecs = np.array(list(self._model.embed(texts)), dtype="float32")
        norms = np.linalg.norm(vecs, axis=1, keepdims=True)
        self.matrix = vecs / norms            # L2 归一化，后续用点积算余弦
```

**第三阶：RRF 融合 + 域外拒识**

```python
def _rrf_fuse(lexical, vector, k=60):
    scores = {}
    for rank, (idx, _) in enumerate(lexical, 1):
        scores[idx] = scores.get(idx, 0.0) + 1.0 / (k + rank)
    for rank, (idx, _) in enumerate(vector, 1):
        scores[idx] = scores.get(idx, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)
```

域外拒识（详见 2.5.4）：

```python
top_sim = vector_top[0][1]
fifth = vector_top[4][1]
confident = top_sim >= 0.55 and (top_sim - fifth) >= 0.02
```

### 3.2.4 降级设计

```python
index = _get_index()
if index is None:
    # fastembed 缺失或模型加载失败 → 静默降级为纯词面
```

这个设计的意义：**部署环境可能没有 GPU、可能装不上 onnxruntime，
但产品不能因此挂掉。**

### 3.2.5 契约稳定性

`search()` 的返回结构是**契约**：

```python
[{task_id, name, app, score, steps}]
```

内部实现从纯词面换成三阶检索，**这个结构一行没变**。

验证：

```python
assert set(r[0].keys()) == {"task_id", "name", "app", "score", "steps"}
```

MCP 的 `search_guide` 依赖它，所以这个约束不能破。

## 3.3 核心功能三：多步卡片

### 3.3.1 数据结构

```python
def compose_card(text, instruction, task_id="", step=1) -> dict:
    task = next((p for p in load_paths() if p["task_id"] == task_id), None)
    steps = task.get("steps") or []
    return {
        "text": text,
        "instruction": instruction,
        "task_id": task_id,
        "task_name": task.get("name", ""),
        "step": step,
        "total_steps": len(steps),
        "current_step": steps[step-1] if 0 < step <= len(steps) else None,
        "next_step":   steps[step]   if 0 < step < len(steps) else None,
        "has_next": step < len(steps),
    }
```

这个结构同时服务两个场景：

1. **前端展示**：显示"第 2 步 / 共 4 步"
2. **多步预热**：`next_step` 直接给出下一步要点什么

### 3.3.2 多步预热的原理

```
第 1 步：老人拍屏 → 定位 → 命中 task_id = wechat.video_call_son
        ↓ compose_card 返回 next_step
第 2 步：不需要重新拍照！
        系统已经知道下一步是「确认当前聊天」
        ↓
第 3、4 步：同理
```

**收益**：4 步任务从 4 次拍照 + 4 次模型调用（约 11 秒）
降到 1 次拍照 + 4 次模型调用（约 3 秒 + 3×1.5 秒）。

> **当前状态**：数据结构与后端能力已就绪，前端尚未接入完整的
> 多步预热交互。这是 W3 的改进项。

### 3.3.3 风险判断（产品红线）

```python
_RISK_RULES = [
```

### 3.4.2 前端叠圈的坐标换算

**这是最容易出错的地方。**

后端返回 `bbox_norm`（0–1000 归一化）。如果图片用 `object-fit: contain`，
实际显示区域和容器不同，**不能直接套百分比**：

```typescript
// web/src/lib/box.ts
export function normToCss(
  box: NormBox,
  naturalW: number,
  naturalH: number,
  containerW: number,
  containerH: number,
) {
  // 先算出 contain 后的实际渲染尺寸
  const scale = Math.min(containerW / naturalW, containerH / naturalH)
  const renderW = naturalW * scale
  const renderH = naturalH * scale
  const offsetX = (containerW - renderW) / 2
  const offsetY = (containerH - renderH) / 2

  return {
    left:   offsetX + (box[0] / 1000) * renderW,
    top:    offsetY + (box[1] / 1000) * renderH,
    width:  ((box[2] - box[0]) / 1000) * renderW,
    height: ((box[3] - box[1]) / 1000) * renderH,
  }
}
```

**如果不做这个换算**，圈会偏移到图片外或错位——这是"第一印象"级别的问题。

### 3.4.3 错误语义的处理

```typescript
try {
  const result = await locate({ image_id, goal })
  session.applyResult(result)
} catch (e) {
  if (e instanceof ApiError && e.status === 422) {
    // 正常拒答，不是故障。展示 detail 让用户重说或重拍
    error.value = new ApiError(422, 'rejected', e.detail)
  } else {
    error.value = e
  }
}
```

**422 和 500 在产品语义上完全不同**：

| 状态 | 语义 | 前端表现 |
|---|---|---|
| 422 | 模型说"看不出该点哪" | 温和提示，可重试 |
| 500 | 服务端异常 | 报错，建议稍后再试 |

## 3.5 本章小结

三个核心功能的实现，共同遵循一条原则：

> **把能确定的做确定，把不确定的诚实说出来。**

| 功能 | 确定性来自 | 不确定时的处理 |
|---|---|---|
| 元素定位 | OCR 给精确坐标 | 模型返回 null → 422 |
| 路径检索 | 120 条人工整理的任务链 | 域外拒识 → 返回空 |
| 多步卡片 | 任务链的步骤是固定的 | `has_next=false` 时明确告知 |

这套设计让产品在现场是**可预期**的——帮助者知道什么时候该信它，
什么时候该重拍或换说法。
